# Track Environments, Vegetation, Sky and Lighting for "Split Ways" (three.js r186, WebGLRenderer, M1 to 4K TV)

Scope: how to build large, realistic outdoor race-track environments that hold 60 fps in the browser on an Apple M1, for 1-4 split-screen viewports. Covers terrain, road, kerbs, run-off, barriers, props, vegetation, grass, distant scenery, sky, fog, time of day, shadows and baked lighting, plus a pipeline from Speed Dreams XML.

Source notes:
- Research date: October 2026.
- Sources dated before 2024 are marked **[older]**.
- "r186 source" means the file was read directly from the project's installed `three@0.186.1` package (`node_modules/.pnpm/three@0.186.1/...`). The GitHub `r186` URL is given for reference.
- Budgets are kept consistent with the sibling note `rendering_platform_performance.md`, section 4 (per viewport: 1.5-3M triangles at 1 viewport, 0.5-1M at 4; about 1,000-1,500 draw calls per frame; GPU at 12-13 ms).

## 1. Terrain: heightmap vs track-aligned meshes, texture splatting (triplanar, macro + detail), breaking tiling (stochastic/hex), blending road into terrain

### Takeaway
Use a hybrid:
- **Near the road:** a track-aligned mesh (road, sides/run-off, borders, barriers) generated from the centre line, so the drivable surface matches physics exactly.
- **Beyond it:** a coarser heightfield terrain that is flattened and stitched to the corridor edge, with a mountain/backdrop ring past that.

Shade terrain with a 4-layer slope/height splat (8 texture fetches with albedo and normal) plus a low-frequency macro variation texture. Use triplanar only on steep faces. Use hex/stochastic tiling only on the one or two layers where repetition shows (grass, gravel). Combining hex tiling with triplanar multiplies texture fetches.

### Cited Findings
- **TORCS/Speed Dreams trackgen** builds the same split [older, still accurate for the data format]:
  - The road and side/border/barrier strips are generated per segment from the XML.
  - The terrain is not stored as geometry. It is generated by trackgen from "Terrain Generation" settings (`"track step"`, `"border step"`, `"terrain transition"`, optional `"elevation map"` or `"relief file"`).
  - Editing the generated road mesh by hand "breaks alignment with physics".
  - [TORCS track manual](https://torcs.sourceforge.net/api/track_manual.html)
- **Splat budget (2026 browser open-world spike):**
  - Slope- and altitude-based splatting with four layers costs 8 fetches per fragment (diffuse plus normal) before lighting; a fifth layer raises it to 10.
  - Triplanar projection on vertical surfaces was judged worth its cost. A fifth splat layer was not.
  - Profiling was done on integrated Intel GPUs within a 16 ms frame.
  - [Cinevva, Open world in the browser part 05 (Feb 2026)](https://app.cinevva.com/blog/2026-02-25-open-world-browser-part-05-budgeting-the-pretty)
- **three-hex-tiling** (three.js library for non-repeating tiling):
  - Splits the texture into hexagonal tiles and blends offset copies.
  - Adds a `hexTiling` material parameter that cannot be toggled after the material is created.
  - Supports only `MeshStandardMaterial` and `MeshPhysicalMaterial`, and was tested on three.js 0.151-0.168 (r186 compatibility unverified).
  - Requires UVs, unlike triplanar mapping.
  - Sources: [three.js forum](https://discourse.threejs.org/t/three-hex-tiling-infinite-non-repeating-seamless-texture-tiling-for-three-js/58251); [npm](https://npmjs.com/package/three-hex-tiling)
- **Hex tiling combined with triplanar** raises the maximum texture fetches to "a whopping 27 for each map used". — [cprimozic, procedural gamedev tools](https://cprimozic.net/blog/tools-and-techniques-for-procedural-gamedev/)
- **Hex-tiling theory:**
  - The technique adapts Heitz and Neyret's by-example noise. Mikkelsen's version (JCGT Vol. 11 No. 2, 2022 [older]) replaces the histogram-preserving precomputation (transform and inverse-transform textures) with a cheap contrast ramp, which makes it easier to adopt.
  - Rotated normal maps need texture gradients/partial derivatives.
  - Sources: [Mikkelsen 2022, JCGT](https://jcgt.org/published/0011/03/05/paper.pdf); [Unity publications](https://unity.com/labs/publications); [Godot shader write-up](https://godotshaders.com/shader/stochastic-hex-tiling-mikkelsens-adaptation/)
- **Stochastic tiling on terrain in other engines:**
  - MicroSplat's stochastic option is described as "a bit more expensive (performance-wise)" than its Anti-Tiling module. — [Unity Asset Store, MicroSplat reviews](https://assetstore.unity.com/packages/tools/terrain/microsplat-texture-clusters-104223/reviews)
  - A Unity forum user said terrain is "the only place where I find tiling to actually become a problem". — [Unity discussions [older]](https://discussions.unity.com/t/procedural-stochastic-texturing-prototype/732031)
- **Terrain at scale in three.js (2025):**
  - A 3072 x 3072 terrain was managed with `BatchedMesh` plus an LOD extension (`batched-mesh-extensions`), with LOD meshes generated by meshoptimizer.
  - [agargaro, "A forest of octahedral impostors" (Aug 2025)](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735)
- **r186 `BatchedMesh` LOD switching:** `addInstance(geometryId)`, `setGeometryIdAt(instanceId, geometryId)` (swap an instance to another LOD geometry), `perObjectFrustumCulled = true`, and `optimize()`. — r186 source, [BatchedMesh.js](https://github.com/mrdoob/three.js/blob/r186/src/objects/BatchedMesh.js)
- **Current project state:** `track/terrain.ts`, `scene/terrainVisual.ts` and `track/trackGeometry.ts` already exist, so road and terrain are generated in code today. — local repo (`client/src/games/splitways/track/`, `scene/`)

### Inferences
- **Recommended terrain structure for the three first tracks:**
  1. **Corridor mesh** (0 to about 40-80 m from the centre line): road, run-off, kerbs and barriers, generated as cross-sections along the centre line (see section 8). It carries a second UV set for lightmaps and track-space UVs (u across, v = metres along the lap).
  2. **Terrain heightfield** (about 80 m to 1-2 km), in chunked tiles of 128-256 m with 2-3 LODs on `BatchedMesh`. Near the corridor, blend terrain height toward the corridor edge with a smoothstep over a shoulder of 10-30 m. To do this, compute a distance-to-centre-line field (a 2D SDF baked into a texture or computed in the generator) and set `h = mix(corridorEdgeHeight, naturalHeight, smoothstep(edge, edge+shoulder, d))`. This mirrors trackgen's `"terrain transition"`.
  3. **Backdrop ring** (more than 2 km): low-poly mountains with baked colour (section 4).
- **Splat recipe:** four layers (short grass, long/dry grass, dirt/gravel, rock), with weights from slope, height, the corridor distance field and an artist paint mask.
  - Store weights in one RGBA splat texture per terrain chunk, or one per track at 0.5-1 m per texel.
  - Add one macro colour/variation texture at 4-16 m per texel, multiplied over everything. This is the cheapest anti-tiling measure and should come first.
  - Use detail textures at 1-4 m tiling.
  - Gate triplanar with `if (slope > threshold)` so only cliffs pay for it. This matters most on the mountain road.
- **Hex tiling:** use it only on the grass and gravel layers, and only at the nearest LOD. Prefer a custom GLSL port of Mikkelsen's contrast-ramp version via `onBeforeCompile` rather than the three-hex-tiling package, whose tested range ends at r168.
- **Don't let terrain own the road surface.** The road should be its own mesh with its own material, overlapped or stitched at the side edge. Seams are hidden by kerbs, grass edges and decal strips.

### Gaps
- No measured M1 cost was found for hex tiling or triplanar in three.js. The 27-fetch figure is a fetch count, not a timing.
- three-hex-tiling compatibility with r186's shader chunks was not verified.
- No published three.js racing-track terrain project (as opposed to open-world terrain) was found.

## 2. Road surface: PBR asphalt with detail and macro variation, racing-line rubber, skid decals, painted lines, kerbs (rumble strips, sawtooth), optional wet roads

### Takeaway
No source documents a browser racing-game road shader. The practical approach is inferred from the data format and the r186 tools:
- Give the road mesh track-space UVs.
- Layer CC0 asphalt detail textures, a macro variation texture, and a low-resolution "track mask" texture (rubber line, paint, dirt, wetness) sampled along the lap.
- Build kerbs as lofted cross-sections from the XML `border` (`style="curb"`, `height`).
- Use `DecalGeometry` or projected strips for skid marks and paint.

AAA references (GT7) show that real surfaces carry tyre marks, oil stains and graffiti, captured by photogrammetry. Laser-scanned road detail was cut to about 10 mm resolution on PS4.

### Cited Findings
- **TORCS/Speed Dreams XML road and kerb data** [older format, still the data we have]:
  - Main track has `"width"`, `"surface"` and `"profil steps length"`.
  - Segments have `"banking start"`/`"banking end"`, `"z start"`/`"z end"` and `"profil"` (`linear`/`spline`).
  - Borders have `"width"`, `"height"`, `"surface"` and `"style"` (`plan`, `curb`, `wall`). For `curb`, `height` is "a cross-width elevation offset".
  - Barriers have `"style"` (`fence`, `wall`) and `"height"`.
  - [TORCS track manual](https://torcs.sourceforge.net/api/track_manual.html)
- **Speed Dreams' track segment struct** uses a main-road type plus left/right side, left/right border and barrier style values. — [Speed Dreams code, Forge commit](https://forge.a-lec.org/speed-dreams/speed-dreams-code/commit/136ec02761b11d37f021c66e1bfaeb376f91d2b2)
- **GT7 road capture** [older, 2021-2022]:
  - The scanner "can pick up to 3mm of resolution", but "most of the tracks in game only have 10mm detail resolution on its surface" because of PS4 limits.
  - Surfaces include "tire marks, oil stains, and even graffiti" from photogrammetry.
  - Sources: [GTPlanet, How Gran Turismo is Made](https://gtplanet.net/how-gran-turismo-is-made); [GTPlanet CEDEC 2022 coverage](https://www.gtplanet.net/pd-circuit-scanning-creation-techniques-20220831/)
- **r186 `LoftGeometry`** (new addon) "generate[s] a geometry by lofting (skinning) a surface through a series of cross sections". Sections can "change shape, size, position and orientation from one section to the next". Options are `closed` (set false for an open strip/ribbon), `capStart` and `capEnd`. — r186 source, [LoftGeometry.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/geometries/LoftGeometry.js)
- **r186 `DecalGeometry`** addon is present for projected decals. — r186 source, [DecalGeometry.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/geometries/DecalGeometry.js)
- **r186 textures:** `Texture.channel` selects which UV set a map uses; the WebGL program builder reads `material.lightMap.channel`. This allows tiling detail UVs (channel 0), lightmap UVs (channel 1) and a third track-space UV set. — r186 source, [Texture.js](https://github.com/mrdoob/three.js/blob/r186/src/textures/Texture.js)
- **CC0 texture sources** usable commercially:
  - Poly Haven: about 780+ textures and 980+ HDRIs. ambientCG: about 2,000+ materials and 400+ HDRIs. Both CC0, no attribution required.
  - FreePBR is not CC0; commercial use requires payment.
  - This rests on one vendor guide; verify per asset.
  - [Cinevva free textures guide (2026)](https://app.cinevva.com/guides/free-textures-hdris-materials)
- **Project already has skid marks:** `scene/skidMarks.ts`. — local repo

### Inferences
- **Road UVs:**
  - Generate u = lateral metres from the left edge (or 0..1 across) and v = metres along the lap. Detail maps use `v/tile` with a tile of 4-8 m.
  - A second channel holds lightmap UVs (packed charts).
- **Asphalt material** (`MeshStandardMaterial` / `MeshPhysicalMaterial`, patched with `onBeforeCompile`):
  - Detail albedo/normal/roughness from a CC0 asphalt set, as KTX2 (UASTC for the normal map).
  - A macro variation texture over the whole track (darker patches, repairs, colour shifts), sampled with track UVs at about 1-2 m per texel.
  - A **track mask** RGBA texture sampled with (u across, v along), about 64-128 texels across the road and 0.25-0.5 m per texel along it:
    - **R:** racing-line rubber, which darkens albedo and slightly lowers roughness.
    - **G:** painted lines (pit exit, start grid, edge lines) when not modelled.
    - **B:** dirt/marbles off-line.
    - **A:** wetness/puddles.
  - A 5.9 km lap at 0.5 m per texel is about 11,800 texels long. This exceeds 8,192, so either fold the strip into a 2D atlas (rows of about 2,048 texels) or split the mask per track chunk.
  - The racing line can be generated automatically from the AI racing line (trackgen even has a `-r` raceline option). Blur it across about 1.5-2 m and modulate it by corner entry and braking zones.
- **Painted lines and kerbs:** model them as geometry strips 1-3 mm above the road (or use `polygonOffset`) rather than decals, so they can be lightmapped and batched.
- **Kerb generation from XML `border style="curb"`:**
  - Loft a cross-section with the authored `width`/`height`.
  - **Sawtooth/rumble profile:** displace the cross-section per step along v with a periodic function (for example a 0.1-0.2 m pitch). Alternatively, keep the geometry flat and use a normal and parallax-occlusion map. Geometry looks better at the camera heights used in racing.
  - Red/white stripes come from a 1D texture in v (stripe length about 1-2 m) so stripes follow curvature exactly.
  - Tag the physics surface (rumble) from the same data so haptics and audio match.
- **Skid decals:** keep the existing skid-mark system for dynamic marks. Bake static "historical" braking marks into the track mask (R channel) so they cost nothing at runtime.
- **Wet road (optional, later):**
  - Darken albedo and push roughness toward glossy on the mask's wet areas.
  - Rely on the HDRI/sky environment for reflections. Planar reflections or SSR per viewport would multiply cost by the viewport count in split screen.
  - Puddles can use the A channel with a flat normal and very low roughness.

### Gaps
- No published three.js or WebGL racing-game road shader was found to cite. The material recipe above is inference.
- No source was found on how Forza, ACC or GT7 author the racing line or rubber build-up visually.
- No measured cost was found for parallax-occlusion kerbs vs geometry kerbs in three.js.

## 3. Vegetation at scale: InstancedMesh/BatchedMesh with LOD, octahedral impostors and three.js impostor libraries, alpha-to-coverage vs alpha test with MSAA, wind in vertex shaders, grass, realistic instance counts on an M1

### Takeaway
The three.js ecosystem in 2025-2026 has proven pieces:
- **Trees:** agargaro's `InstancedMesh2` (BVH frustum culling plus per-instance LOD) and the `octahedral-impostor` library (MIT). A demo shows 200k trees with mesh LOD to 100 units and impostors beyond.
- **Grass:** clumps on quads (about 3M total triangles as a forum rule of thumb), chunked LOD, and wind from a scrolling noise texture. A commercial WebGPU grass system reports a locked 60 fps at 1440p on an M1 Mac.

For foliage edges with the project's MSAA HDR target, use `material.alphaToCoverage = true` with alpha sharpening and mip-alpha scaling. Use `alphaHash` or alpha test where MSAA is off.

A racing game should spend its vegetation budget on tree lines and bushes seen at 30-500 m, plus short grass cards right at the track edge. Dense 3D blade fields are not the priority.

### Cited Findings
- **agargaro forest demo (Aug 2025):**
  - 200k trees in `InstancedMesh2` with a BVH for frustum culling.
  - LOD1 is a meshoptimizer-simplified mesh at about 15-100 units; an octahedral impostor is used beyond 100 units.
  - Terrain uses `BatchedMesh` with LODs.
  - Impostor settings: `useHemiOctahedron: true`, `spritesPerSide: 16`, `textureSize: 2048`, `transparent: false`, `alphaClamp: 0.45`, `parallaxScale: 0.5`, `baseType: MeshLambertMaterial`.
  - The author does not plan to add dithered/crossfade LOD transitions.
  - No FPS or hardware figures are given.
  - [three.js forum](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735)
- **`octahedral-impostor` repo:** MIT licensed, marked "wip", 87 commits. — [GitHub agargaro/octahedral-impostor](https://github.com/agargaro/octahedral-impostor)
- **InstancedMesh2 (three.ez):** "enhanced InstancedMesh with frustum culling, fast raycasting (BVH), sorting, visibility management, LOD, skinning". LOD API example: `trees.addLOD(boxGeo, new MeshLambertMaterial(), 100)`. — [three.js forum, InstancedMesh2](https://discourse.threejs.org/t/three-ez-instancedmesh2-enhanced-instancedmesh-with-frustum-culling-fast-raycasting-bvh-sorting-visibility-management-lod-skinning-and-more/69344)
- **Impostor practicalities** (Usnul, same thread):
  - A 5-vertex (3-triangle) convex hull around the sprite removed "about 30% of pixels on average".
  - LOD crossfading draws two LODs during the transition, so it can cost more than the higher LOD alone.
  - Popping mainly comes from too little angular resolution.
  - [three.js forum](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735)
- **Impostor implementation lessons (May 2026 browser open-world series):**
  - Bake two atlases per prop: unlit diffuse plus world-space normals (`normal*0.5+0.5`), with alpha copied from the source. Render with a full `MeshStandardNodeMaterial` so impostors still receive sun and IBL.
  - Plain octahedral mapping caused CPU/GPU tile-selection divergence at fold boundaries. Hemi-octahedral mapping removes the pole singularity.
  - Bilinear blending of the 2x2 nearest tiles costs 8 taps (4 diffuse, 4 normal).
  - A 12x12 hemi-octahedral atlas is about 9 MB vs 1.6 MB for an azimuth/elevation layout, and takes about 5x longer to bake (288 render passes).
  - The pipeline is GPU-driven: per-instance centre/yaw/scale attributes uploaded once, and a per-frame CPU cost of one camera-uniform copy.
  - three.js frustum-culled the whole instanced forest until an explicit bounding sphere was set.
  - The target was one million trees.
  - [Cinevva part 19 (May 2026)](https://app.cinevva.com/blog/2026-05-04-open-world-browser-part-19-imposters)
- **Vegetation scattering lessons (Feb 2026):**
  - Runtime scattering into `InstancedMesh` sets.
  - Wind in the vertex shader from a scrolling noise texture.
  - "Batching instances into fewer meshes mattered more than reducing per-blade polygon count".
  - Density maps of 32x32 per terrain chunk.
  - WebGPU `ComputeInstanceCulling` and `IndirectBatchedMesh` (multi-draw indirect) were noted as scaling options but not measured.
  - [Cinevva part 05](https://app.cinevva.com/blog/2026-02-25-open-world-browser-part-05-budgeting-the-pretty)
- **Grass budget rule of thumb (forum, Apr 2025):**
  - "Safe/sweet spot for total number of triangles is ~3million". A 20-triangle blade at 3M instances is "about 20x over budget".
  - "Do clumps of grass on quads instead"; with quads "you can probably push a few million of them".
  - Merging blades into clumps can shift the bottleneck to vertex/triangle bound.
  - Sort front to back to cut overdraw.
  - This is a single expert's opinion, not a benchmark.
  - [three.js forum, 3M instanced grass](https://discourse.threejs.org/t/performance-optimizing-3m-instanced-grass-in-three-js/81286)
- **Commercial grass system on M1 (Jul-Aug 2026):**
  - "Locked 60fps at 1440p" on an M1 Mac (and on an M1 Mac mini), up from about 40 fps before optimization. Uses WebGPU.
  - Features: per-blade frustum culling on visible tiles, crossfade LOD, a billboard grass mode, up to 8 interacting objects, and paint masks saved as JPG.
  - Closed source, to be sold as a plugin.
  - No blade counts were given.
  - A depth prepass for vegetation was suggested, citing GDC's Horizon Zero Dawn vegetation talk.
  - [three.js forum](https://discourse.threejs.org/t/migrating-my-grass-system-to-webgpu-and-making-a-robust-grass-plugin/92893)
- **Codrops "fluffiest grass" tutorial:** per-chunk LOD with three detail levels, and distant grass culled to save draw calls. It ran on a 2018 Intel i3 laptop and used fog to hide pop-in. — [Codrops](https://tympanus.net/codrops/?p=83092) (from search summary; page not fetched)
- **Ghost of Tsushima** (GDC 2021 [older]): grass is generated per blade on the GPU with procedural shape and animation. Community reimplementations note that blades perpendicular to the camera are widened in view space and bent by height. No per-tile counts are public. — [GDC Vault](https://gdcvault.com/play/1027214/Advanced-Graphics-Summit-Procedural-Grass); [GodotGrass](https://github.com/2Retr0/GodotGrass)
- **Alpha-to-coverage:**
  - Ben Golus's article (2017 [older]) assumes "forward rendering with at least 4x MSAA". Alpha-tested foliage aliasing "is shader aliasing which generally MSAA can't help with". A2C fixes it, combined with a mip-level alpha scale. — [Golus, Medium](https://bgolus.medium.com/anti-aliased-alpha-test-the-esoteric-alpha-to-coverage-8b177335ae4f)
  - 4x MSAA gives only five coverage levels, so quantization artifacts appear. — [Wikipedia: Alpha to coverage](https://en.wikipedia.org/wiki/Alpha_to_coverage)
  - A2C loses alpha density at distance due to mipmapping. Scaling alpha fixes it but makes near foliage denser and slightly jagged. — [gamedev.net foliage thread [older]](https://www.gamedev.net/forums/topic/540726-foliage-rendering/4492102/?page=1)
  - Plain alpha testing aliases on texture-space alpha boundaries, which geometric AA cannot fix. Hashed alpha testing is the stochastic alternative. — [Wyman & McGuire 2017, NVIDIA [older]](https://research.nvidia.com/sites/default/files/pubs/2017-02_Hashed-Alpha-Testing/Wyman2017Hashed.pdf)
  - r186 `Material` has both `alphaToCoverage` and `alphaHash` properties. — r186 source, [Material.js](https://github.com/mrdoob/three.js/blob/r186/src/materials/Material.js)
- **AAA and modding tree practice:**
  - GT: trees are the hardest environmental element, made "as realistic and believable as possible without creating too much load". — [GTPlanet, How Gran Turismo is Made [older]](https://gtplanet.net/how-gran-turismo-is-made)
  - Assetto Corsa: the `KsTree` shader suits X- or Y-shaped tree cards; grass comes from CSP GrassFX. — [assettocorsamods.net](https://assettocorsamods.net/threads/assetto-mods-and-track-creation.3349)
  - A Kyalami AC mod peaked at about 5 million triangles, which is why grass LOD matters. — [assettocorsamods.net Kyalami thread](https://www.assettocorsamods.net/goto/post?id=10540)

### Inferences
- **Speed changes the priorities.** At 200-300 km/h (55-85 m/s), anything within about 10 m of the camera streaks past in a fraction of a second.
  - Vegetation that matters: continuous tree lines and bush belts at 20-300 m that frame corners, plus a believable ground texture at the track edge.
  - Near-camera 3D grass blades matter little except on slow sections, the grid, replay/photo cameras and the mountain road.
- **Per-type plan (estimates, to be profiled on the M1):**

| Layer | Technique | Range | Visible instances per viewport (1 vp / 4 vp) | Notes |
|---|---|---|---|---|
| Hero trees near track | `InstancedMesh2` LOD0 mesh (3-8k tris, A2C leaves) → LOD1 meshoptimizer (500-1.5k) | LOD0 < 40-60 m, LOD1 to 120-150 m | LOD0 30-80 / 10-30; LOD1 150-400 / 80-200 | 4-8 species × 2-3 variants; shadow casters only for LOD0/LOD1 |
| Far trees | Hemi-octahedral impostors (16×16 frames, 2048² atlas, albedo + normal) | 120 m to fog end | 2k-20k / 2k-10k | 1 draw call per species; opaque with alpha clamp, or A2C |
| Forest mass / hillsides (more than 500 m) | Baked into the terrain/backdrop texture plus a few impostor "clusters" | more than 500 m | 0 extra | Atmospheric perspective hides it (section 4) |
| Bushes | Card clusters (8-30 quads), instanced | to 150 m | 300-1,500 / 100-500 | Wind on leaves only |
| Grass near track | Instanced clump quads (2-6 tris) in tiles, density from the splat/paint mask | 0-25 m (1 vp), 0-12 m (4 vp) | 50k-200k quads / 15k-50k | Fade by distance; no shadows cast; disable on Low |
| Grass mid distance | None. The terrain texture carries it (macro + detail + normal) | — | — | — |

- **Triangle maths:** 200k grass quads is 400k triangles. Trees add roughly 0.3-1M (LOD0 40 × 5k + LOD1 300 × 1k + impostors 10k × 2-6). That fits inside the 1.5-3M per-viewport budget with the track, cars and props. At 4 viewports, halve these figures.
- **Draw calls:**
  - One `InstancedMesh2` per species per LOD, plus one impostor mesh per species.
  - Grass as one instanced mesh per tile ring, or one `BatchedMesh`.
  - Target fewer than 60 vegetation draw calls per viewport, plus shadow-pass calls only for LOD0/LOD1 trees.
- **Alpha:**
  - The project's HDR target is a half-float MSAA render target, so A2C works on leaves and grass. Enable `alphaToCoverage`.
  - Compute alpha in the shader as `(a - cutoff) / max(fwidth(a), 1e-4) + 0.5` (Golus-style sharpening).
  - Preprocess mips to preserve alpha coverage, or scale alpha by mip level.
  - On Low presets where MSAA is off, fall back to `alphaTest` (or `alphaHash` if a temporal AA ever exists).
  - Keep impostors opaque (`transparent: false` with an alpha clamp), as in the agargaro demo.
- **Wind:** one shared scrolling noise texture plus a per-instance phase, as in Cinevva and the forum examples.
  - **Trunks:** sway weighted by height.
  - **Leaves:** high-frequency flutter weighted by a vertex colour channel.
  - **Grass:** bend weighted by blade height.
  - Keep wind off impostors, or apply a tiny UV wobble.
- **Licensing:** agargaro's libraries are MIT. The commercial grass plugin is closed source. Tree meshes should be CC0 (Poly Haven, ambientCG and similar) or custom; verify each asset.

### Gaps

- `octahedral-impostor`'s npm name, API and three.js version support were not readable from the GitHub page; read package.json before use.

## 4. Distant scenery and sky: mountains (low-poly + baked textures, HDRI/skybox layers), atmospheric perspective; sky models (Sky addon / SkyMesh, Preetham/Hosek/Bruneton), clouds, time of day

### Takeaway
r186's WebGL `Sky` addon is a Preetham analytic sky that now includes procedural 2D fbm clouds (coverage, density, elevation, scale, speed). `SkyMesh` is the WebGPU version with the same uniforms. Together with sun-direction-aware exponential/height fog, this is enough for good time-of-day skies at almost no cost.

`@takram/three-atmosphere` and `@takram/three-clouds` (Bruneton precomputed scattering plus volumetric clouds) are a quality step up. They are beta, need the pmndrs `postprocessing` EffectComposer, and their post-process lighting mode is Lambert-only, so they fit poorly with the project's custom HDR pipeline.

For mountains, use real DEM data (Copernicus GLO-30 is free with attribution) turned into low-poly meshes with baked colour, faded into the sky with atmospheric perspective. An HDRI layer can be used for the static-ToD option.

### Cited Findings
- **r186 `Sky` (WebGL) uniforms and defaults:**
  - `turbidity` 2, `rayleigh` 1, `mieCoefficient` 0.005, `mieDirectionalG` 0.8, `sunPosition`.
  - Clouds: `cloudScale` 0.0002, `cloudSpeed` 0.00002, `cloudCoverage` 0.4, `cloudDensity` 0.4, `cloudElevation` 0.5.
  - Also `showSunDisc` 1 and `time`.
  - Clouds are fbm noise projected onto a plane (`cloudUV = direction.xz / (direction.y * elevation)`) with "per-octave drift" so they "billow instead of scrolling".
  - r186 source, [Sky.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/objects/Sky.js)
- **`SkyMesh`:**
  - WebGPURenderer only ("For WebGLRenderer, use Sky"). Based on Preetham, "A Practical Analytic Model for Daylight".
  - Uniforms: `turbidity`, `rayleigh`, `mieCoefficient`, `mieDirectionalG`, `sunPosition`, `showSunDisc`, `cloudCoverage`, `cloudDensity`, `cloudElevation`, `cloudScale`, `cloudSpeed`.
  - Turn off `showSunDisc` while generating an environment map to avoid artifacts.
  - [three.js docs, SkyMesh](https://threejs.org/docs/pages/SkyMesh.html)
- **`@takram/three-atmosphere`:** a three.js/R3F implementation of Bruneton's precomputed atmospheric scattering. It has a post-process mode (suits large scenes, but "only supports Lambertian shading" and requires unlit materials) and a light-source mode. — [README v0.13.2](https://unpkg.com/@takram/three-atmosphere@0.13.2/README.md)
- **`@takram/three-clouds`:**
  - Volumetric clouds with Beer shadow maps, temporal upscaling, light shafts and haze.
  - Runs inside an EffectComposer before `AerialPerspective`.
  - At most 4 cloud layers.
  - Requires the `postprocessing` library's EffectComposer, not the three.js examples one.
  - Sources: [README v0.7.4](https://cdn.jsdelivr.net/npm/@takram/three-clouds@0.7.4/README.md); [three-geospatial docs index](https://docsearch.algolia.com/mcp/docs/repo/takram-design-engineering/three-geospatial)
  - Both packages are marked beta, with WebGPU support in progress (aggregator source, lower confidence). — [trendshift](https://trendshift.io/admin/repository/ask-ai/13111)
- **Inigo Quilez fog** [older]:
  - Tint fog toward the sun colour by a power of `dot(viewDir, sunDir)`. He notes this is really light scattering, but it can be done by modifying the fog equation.
  - Analytic height fog: density falls off with height and integrates along the ray.
  - The published height-fog formula divides by the ray's vertical component, which breaks for level rays (community report).
  - Sources: [iquilezles.org/articles/fog](https://iquilezles.org/articles/fog/); [MonoGame forum](https://community.monogame.net/t/solved-height-distance-based-fog-again/14371)
- **Copernicus DEM GLO-30** (30 m global elevation):
  - Free and open under the Copernicus DEM licence.
  - Distributors must credit DLR/Airbus with a prescribed notice (a different notice for modified data) and include a liability disclaimer.
  - The excerpts seen did not quote an explicit commercial-use clause; read the full licence.
  - Sources: [Licence PDF](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/DEM/resources/license/License-COPDEM-30.pdf); [AWS Open Data registry](https://registry.opendata.aws/copernicus-dem/)
- **GT7's Kyoto Driving Park:** the landscape team scanned the terrain and plants at the real location (a mountain basin north of Kyoto) and photographed the Kitayama cedars. — [GTPlanet CEDEC 2022 [older]](https://www.gtplanet.net/pd-circuit-scanning-creation-techniques-20220831/)
- **Current project:** has `render/sky.ts`, `render/haze.ts` and `render/sun.ts`, with an HDRI sky and fog chunks replaced via `ShaderChunk`. — local repo (`client/src/games/splitways/render/`)

### Inferences
- **Sky choice:**
  - For dynamic time of day on WebGL, use r186 `Sky` with clouds, which costs one fullscreen-ish pass per viewport. Render it at reduced resolution into a cube or low-res texture only when the sun moves.
  - Reuse the same sky to regenerate the scene environment (PMREM) occasionally, for example every few seconds or when the ToD step changes, with `showSunDisc` off during capture.
  - For a fixed "hero" time of day, a CC0 HDRI (Poly Haven) gives better clouds and lighting than Preetham. Keep it as the High preset backdrop for fixed-ToD races.
- **Bruneton (takram):** good reference quality, but defer it. It is beta, the clouds need pmndrs `postprocessing`, and the post-process mode forces Lambert, which conflicts with the custom HDR pipeline and PBR cars. Its volumetric clouds are also likely too expensive at 4 viewports on an M1.
- **Hosek-Wilkie:** a possible upgrade over Preetham for low sun angles. It is not in three.js, so it would need a port (see Gaps).
- **Mountains / backdrop:**
  1. Fetch a DEM (Copernicus GLO-30) for a chosen real region, or synthesise one with erosion noise for fictional tracks.
  2. Decimate rings beyond 2 km to about 50-200k triangles total (1 draw call).
  3. Bake colour (albedo × sky light × AO, slope-based rock/snow/forest) into one 4-8k texture, and ship it as KTX2.
  4. Render it unlit (or simply lit) with strong distance fog.
  - For the mountain road, the near terrain is itself mountains, so the backdrop ring only covers the far valley sides.
- **Atmospheric perspective** in the existing fog chunk:
  - Fog colour = mix(skyHorizonColour, sunScatterColour, pow(max(dot(v, sunDir), 0), 8)).
  - Exponential density plus IQ-style height falloff, guarded against `rd.y≈0`.
  - Sample the horizon colour from the same `Sky` uniforms so mountains always melt into the sky at every time of day.
- **Time of day:** drive sun position, `Sky` uniforms, fog colours, exposure and light intensity from one keyframed table. Static track lighting must then be ToD-independent or re-baked (section 6).

### Gaps
- No three.js Hosek-Wilkie implementation or cost figure was found.
- No measured cost was found for takram atmosphere/clouds on an M1. The takram licence was not verified.
- The release in which `Sky` gained clouds was not identified (it is present in r186).
- No AAA racing-game source on backdrop mountain techniques (Forza/GT) was found.

## 5. Shadows: CSM for WebGL, CSMShadowNode for WebGPU, map sizes, PCF/PCSS/VSM cost, contact shadows/ground AO under cars

### Takeaway
r186 has three cascaded-shadow options:
1. The older `CSM` addon (WebGL; per-material `setupMaterial`; defaults 3 cascades, 2048² maps).
2. `CSMShadowNode` (WebGPU only).
3. A new `SunLight` addon with built-in 2-cascade CSM wired into the core WebGL shader chunks. It defaults to 1024² per cascade with a 10% fade band, and also works on WebGPU via `SunLightNode`.

`PCFSoftShadowMap` is deprecated in r186 and falls back to hardware-filtered `PCFShadowMap`. VSM remains, but makes every receiver a caster.

For split screen, the cascades are re-rendered per viewport camera. The cheapest robust design is:
- Bake static track shadows/AO into lightmaps.
- Use dynamic shadows only for cars, plus near trees and props on High.
- Add a cheap blob/contact AO under each car.

Measured browser data: 3 cascades at 1024² stayed under 2 ms, and 3-4 cascades at 1024² cost about 0.5-1 ms to render plus 0.2-0.3 ms to sample.

### Cited Findings
- **`CSM` (WebGL addon):**
  - Import from `three/addons/csm/CSM.js`.
  - Defaults: `cascades` 3, `maxFar` 100000, `mode` `'practical'` (or `uniform`/`logarithmic`/`custom` with `customSplitsCallback`), `shadowMapSize` 2048, `shadowBias` 0.000001, `lightIntensity` 3, `lightNear` 1, `lightFar` 2000, `lightMargin` 200, `fade` false.
  - Call `setupMaterial(material)` for every receiving material, `update()` every frame before render, and `updateFrustums()` when camera settings change.
  - WebGLRenderer only.
  - [three.js docs, CSM](https://threejs.org/docs/pages/CSM.html)
- **`CSMShadowNode`:** WebGPURenderer only. Takes `(light, data)`, defaults to 3 cascades, and has `breaks`, `fade` and `customSplitsCallback`. — [three.js docs, CSMShadowNode](https://threejs.org/docs/pages/CSMShadowNode.html)
- **CSM drawbacks** (forum): it rasterizes many pixels, can be memory-heavy, and is resolution-dependent, so cascade count and resolution must be chosen. — [three.js forum, CSM on WebGPU](https://discourse.threejs.org/t/cascaded-shadow-maps-csm-on-webgpu/84235)
- **r186 `SunLight` + `SunLightShadow` (new addons):**
  - "A sun-like light ... casts cascaded shadow maps via SunLightShadow, suited for lighting large scenes". Its direction is defined by its position (no target).
  - Uses **two cascades** (`_cascadeCount = 2`, "must match the cascade count in the sun shadow shader chunks") with `_cascadeFade = 0.1`.
  - "The default mapSize is 1024x1024 per cascade". The projection is "fitted automatically to slices of the view frustum, up to ... camera.far".
  - Supported natively by WebGLRenderer: core chunks reference `NUM_SUN_LIGHT_SHADOWS` and `getSunShadow`, which walks the cascades with fade blending.
  - On WebGPU, register with `renderer.library.addLight(SunLightNode, SunLight)`.
  - r186 source: [SunLight.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/lights/SunLight.js), [SunLightShadow.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/lights/SunLightShadow.js), [shadowmap_pars_fragment](https://github.com/mrdoob/three.js/blob/r186/src/renderers/shaders/ShaderChunk/shadowmap_pars_fragment.glsl.js)
- **r186 shadow map types:**
  - `PCFSoftShadowMap` is "@deprecated since r186. Use PCFShadowMap instead". WebGLShadowMap warns "PCFSoftShadowMap has been removed. Using PCFShadowMap instead."
  - The PCF path samples a `sampler2DShadow` (hardware comparison).
  - "When using VSMShadowMap all shadow receivers will also cast shadows".
  - r186 source, [constants.js](https://github.com/mrdoob/three.js/blob/r186/src/constants.js), [WebGLShadowMap.js](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLShadowMap.js)
- **Measured cascade cost (2026 browser open-world spikes):**
  - "Three cascades at 1024 stayed under 2 ms of GPU time on the target hardware".
  - "3-4 cascades at 1024x1024 add about 0.5-1 ms for shadow map rendering and about 0.2-0.3 ms for sampling".
  - Low sun angles stress the cascades most.
  - Hardware: integrated Intel, not an M1.
  - [Cinevva part 05](https://app.cinevva.com/blog/2026-02-25-open-world-browser-part-05-budgeting-the-pretty)
- **Current project:** one directional light whose shadow covers "a tight box around whichever car is being rendered", re-aimed before each viewport because "three.js re-renders the shadow map on every render call". Map size comes from `RENDER.shadowMapSize`, with `bias -0.0004` and `normalBias 0.03`. — local repo, `client/src/games/splitways/render/sun.ts`
- **Sibling budget note:** at 4 viewports, use one shared 2048-4096² sun map, skip per-viewport cascades, and use contact shadows or blob AO under cars. — local note, `rendering_platform_performance.md` §4
- **r186 `LightProbeGridWebGL` bake** temporarily replaces shadow-casting `SunLight`s with directional lights, "since their view-fitted shadow cascades cannot be frozen across probe renders". This confirms the cascades are per-view-camera. — r186 source, [LightProbeGridWebGL.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/lighting/LightProbeGridWebGL.js)

### Inferences
- **Recommended preset ladder** (estimates; profile on the M1):

| Preset | Static track shadows | Dynamic shadows | Map size | Filter | Under-car |
|---|---|---|---|---|---|
| Low (4 vp) | Baked in lightmap (fixed ToD) or none | Cars only, one tight box per car (current `sun.ts` approach), or none | 1024² | PCF | Blob/contact AO quad |
| Medium (2-4 vp) | Baked | `SunLight` 2 cascades: cars + near trees/props; static terrain receives only | 1024² per cascade | PCF | Blob AO |
| High (1-2 vp) | Baked + dynamic overlap near camera | `SunLight` 2 cascades or `CSM` 3 cascades, `maxFar` 150-250 m | 2048² near, 1024² far | PCF (radius 1-2) | Blob AO + GTAO if budget allows |

- **Split-screen cost:** both `SunLight` and `CSM` fit cascades to the view camera, so shadow maps are re-rendered once per viewport. To limit this:
  - Shadow casters should be a small layer set (cars, LOD0/LOD1 trees, props within about 100 m), not the whole track. Use layers or `castShadow=false` on terrain, road, impostors and grass.
  - Keep `maxFar` short (150-250 m). Beyond that, baked lighting carries the shadows.
- **Choosing between CSM and SunLight:** prefer `SunLight` over `CSM` on WebGL. It is wired into the core shader chunks, so there is no `setupMaterial` patching (which would conflict with the project's own `onBeforeCompile`/ShaderChunk changes), and it supports WebGPU later via `SunLightNode`. Use `CSM` only if more than 2 cascades turns out to be necessary on High.
- **Filters:**
  - **PCSS:** soft contact-hardening costs many taps. Reserve it for single-viewport photo/replay modes.
  - **VSM:** makes every receiver a caster, which conflicts with "terrain receives only". Avoid it.
- **Under-car grounding:**
  - A per-car blob/AO quad (a baked AO texture of the car footprint, multiplied into the ground) costs about one draw per car and is effectively free.
  - Contact shadows via depth rendering cost more per viewport.
  - This is how most racing games keep cars grounded when dynamic shadows are low resolution.

### Gaps
- No M1-specific shadow timings were found. The cascade cost numbers come from integrated Intel GPUs.
- No measured PCSS or VSM cost in three.js r186 was found. The three.js contact-shadow and PCSS examples were not re-verified for r186.
- It is unclear whether r186's `SunLight` cascade count (fixed at 2) or fade can be changed without editing the shader chunks.

## 6. Baked lighting: lightmaps/AO baked in Blender (Cycles) for static track geometry, light probes/irradiance volumes in three.js, shipping baked data efficiently

### Takeaway
Bake static lighting in Blender Cycles into a second UV set:
- glTF carries `TEXCOORD_1` by default, but there is no standard lightmap extension, so the lightmap is assigned in code via `material.lightMap` with `texture.channel = 1`.
- Ship lightmaps as KTX2. r186's KTX2Loader supports BasisU UASTC HDR, transcoding to BC6H or ASTC HDR when available.

For dynamic objects (cars), r186 adds `LightProbeGridWebGL` / `LightProbeGrid`: an L2 spherical-harmonics irradiance volume baked on the GPU at runtime. It supports bounces and incremental (ranged) baking, so it can be baked at load time instead of shipped.

Because the project wants time of day, the lightmap should store ToD-independent terms (sky occlusion/AO and bounce from a neutral sky). The direct sun stays dynamic. Alternatively, bake one full lightmap set per fixed ToD preset.

### Cited Findings
- **r186 `LightProbeGridWebGL`:**
  - "A 3D grid of L2 Spherical Harmonic irradiance probes that provides position-dependent diffuse global illumination". Only for WebGLRenderer; "For WebGPURenderer, use LightProbeGrid".
  - Constructor: `(width, height, depth, widthProbes, heightProbes, depthProbes)`, "centered at the object's position".
  - "Baking is fully GPU-resident: cubemap rendering, SH projection, and texture packing all happen on the GPU with zero CPU readback". All seven packed SH sub-volumes are stored in one RGBA `WebGL3DRenderTarget`.
  - `bake(renderer, scene, { cubemapSize = 8, near = 0.1, far = 100, bounces = 0, start, count, pass })`. `start`/`count` allow baking a range of probes per frame.
  - WebGLRenderer pushes `isLightProbeGrid` objects into render state and picks the grid per object.
  - r186 source, [LightProbeGridWebGL.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/lighting/LightProbeGridWebGL.js); [WebGLRenderer.js](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js)
- **r186 `LightProbeGrid` (WebGPU):** "The bake is node based, so it needs a WebGPURenderer"; it is applied to lit node materials automatically. — r186 source, [LightProbeGrid.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/lighting/LightProbeGrid.js)
- **Forum context (Apr-May 2026):**
  - The light-probe volume "provides diffuse GI via L2 Spherical Harmonics probe grid" (corrected from L1 in PR #33505). The example is `webgl_lightprobes`.
  - At that time it was "not yet available for WebGPU as it's experimental"; r186 now ships a WebGPU version.
  - Usnul suggested L1 for diffuse-only work because L2 costs about twice the ALU.
  - [three.js forum, Global Illumination](https://discourse.threejs.org/t/global-illumination/91243)
- **Single-probe tool:** `LightProbeGenerator` covers single probes (from cube textures/render targets). — [three.js docs](https://threejs.org/docs/pages/LightProbeGenerator.html)
- **r186 lightmap UV selection:** `Texture.channel` (default 0). The WebGL program reads `lightMapUv: getChannel(material.lightMap.channel)`. — r186 source, [Texture.js](https://github.com/mrdoob/three.js/blob/r186/src/textures/Texture.js), [WebGLPrograms.js](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLPrograms.js)
- **glTF and lightmaps:** glTF "supports multiple texCoords (UV sets) by default", but "there is no extension for lightmaps in glTF so you will need to wire those textures up in your scene manually". — [Babylon.js forum](https://forum.babylonjs.com/t/glb-exports-tileable-textures-lightmaps-baked-lights/17701)
- **Lightmap UVs must not overlap**; community extensions (MX_lightmap, MOZ_lightmap) store the texCoord index. — [HackMD, lightmapping for the web](https://hackmd.io/@XR/lightmapping-web); [three.js forum, Blender lightmaps](https://discourse.threejs.org/t/apply-uv-coordinates-and-lightmaps-baked-from-blender-to-mesh/63910)
- **Blender batch-baking tools:**
  - `lightmap-bakery`: a Python tool that drives Cycles to bake lightmaps across several .blend files. It creates a new UV map named 'lightmap', joins meshes, and handles static objects only. — [GitHub subgression/lightmap-bakery](https://github.com/subgression/lightmap-bakery)
  - The Lightmapper add-on: automatic UV setup, material setup, denoising, encoding/format options. — [GitHub The_Lightmapper](https://github.com/lordloki/The_Lightmapper)
  - Cycles samples can be set from Python via `bpy.context.scene.cycles.samples`, and scripted bake sequences run serially. — [Blender Artists](https://blenderartists.org/t/b3-2-automatic-bake-sequence/1416420)
  - Convention: "UVMap" for texture coordinates, "uv2" for the shared lightmap. — [rh2 lightmap utility](https://rh2.gumroad.com/l/lightmap)
- **r186 KTX2Loader HDR:**
  - Supports "BasisU HDR" (UASTC HDR).
  - "If the device supports ASTC, Basis UASTC HDR requires no transcoder". Otherwise it transcodes (BC6H among targets).
  - ASTC HDR is detected via `WEBGL_compressed_texture_astc` `getSupportedProfiles().includes('hdr')`.
  - r186 source, [KTX2Loader.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/loaders/KTX2Loader.js)
- **FM7 track LOD** [older]: Turn 10 aimed to auto-generate "90+% of our track object LODs" with Simplygon. A track has tens of thousands of objects, about 2/3 of them with LODs. — [Simplygon case study](https://simplygon.com/posts/5f1e97cd-b9e9-4746-b669-d6d6e893b662)

### Inferences
- **What to bake** (ToD-aware):
  - **Dynamic ToD** (sun moves during or between races):
    - Bake sky visibility/AO plus one bounce from a neutral white sky into a single-channel or RGB lightmap (8-bit is fine; it is a 0-1 multiplier).
    - At runtime: `ambient = skyIrradiance(ToD) × lightmapAO`, and the direct sun comes from `SunLight`.
    - Static shadows from trees and buildings on the road are then dynamic (cascades) or missing beyond `maxFar`. This is acceptable because baked AO grounds everything.
  - **Fixed ToD presets** (for example "Morning", "Golden hour", "Overcast"):
    - Bake full irradiance (sun + sky + bounces) per preset as HDR (UASTC HDR KTX2) or RGBM 8-bit.
    - Gives the best quality and the cheapest runtime: only cars need dynamic shadows, using the current tight per-car shadow box.
    - Costs memory and download size times the number of presets.
  - Recommendation: launch with fixed ToD presets per track (2-3), since Forza Motorsport-style races mostly use a time-of-day choice rather than a live cycle. Add the AO-only path later if live ToD is wanted.
- **Texel density and sizes** (estimates):
  - Road and run-off at about 0.25-0.5 m per texel. Terrain lightmapping is unnecessary beyond the corridor (use vertex AO or the terrain bake).
  - A 5.9 km circuit corridor 60 m wide is about 354,000 m². At 0.5 m per texel that is about 1.4M texels (two 1024² pages); at 0.25 m per texel it is about 5.7M (six 1024² pages).
  - Grandstands and buildings at 0.1-0.2 m per texel in their own atlases.
  - Total of about 4-12 × 1024²-2048² lightmap pages per track: tiny compared with albedo textures.
- **Blender CLI pipeline:**
  - Run headless (`blender -b track.blend --python bake_track.py`). The script:
    1. Imports the generated corridor/terrain glTF.
    2. Adds a "uv2" map and smart-UV-projects it with margin.
    3. Creates bake images.
    4. Bakes with Cycles (AO or combined; direct/indirect pass filters per mode) with denoising.
    5. Saves EXR.
    6. Exports glTF with two UV sets.
  - Then encode with `toktx`/`basisu` to KTX2 (UASTC HDR for full irradiance, ETC1S/UASTC LDR for AO).
  - The exact `bpy.ops.object.bake` parameters must be checked against the Blender API docs (not fetched here).
- **Light probes for cars:** place a `LightProbeGridWebGL` covering the track corridor (for example 4-8 m spacing horizontally, 2-3 layers vertically, in several grids per track section) and bake it at load with `cubemapSize` 8 and 1 bounce. Spread the bake over frames using `start`/`count` during the loading screen or countdown so the car picks up tunnel, grandstand and tree-shade darkening. Alternatively, ship the 3D texture as data.
- **Shipping:** gzip/brotli on Vercel for glTF and binary buffers, Draco/meshopt geometry compression for the corridor meshes, and KTX2 for all textures. Lazy-load the backdrop and impostor atlases after the track becomes drivable.

### Gaps
- Not verified: the exact Blender 4.x/5.x Python bake API arguments, and whether glTF export preserves a custom "uv2" name vs order (it exports as `TEXCOORD_1` by order).
- Unknown whether Chrome on M1 exposes the ASTC HDR profile. If not, UASTC HDR is transcoded (BC6H or uncompressed half-float), which costs memory.
- No measured bake time was found for `LightProbeGridWebGL` with many probes on an M1.

## 7. Lessons from Forza Motorsport, Assetto Corsa Competizione, Gran Turismo 7 (vegetation density, LOD distances, trackside detail) and from web open-world/terrain demos

### Takeaway
AAA studios build tracks from laser scans and photogrammetry, with hand-modelled environments, heavy LOD automation and a strong focus on trees and trackside detail:
- GT7 takes at least 6 months per track, with up to 80,000 photos and 8 TB of capture for one Spa pass.
- Forza aimed to auto-generate 90%+ of track-object LODs across tens of thousands of objects.

No studio publishes vegetation densities or LOD distances. The applicable lessons for a small team are:
1. Spend detail where the camera actually looks: road surface, kerbs, the first barrier line, and tree lines framing corners.
2. Automate LOD (meshoptimizer/Simplygon-style).
3. Use impostors for everything far.
4. Use web demos' measured patterns: batch more than reduce polycount, 4 splat layers maximum, about 3 cascades at 1024².

### Cited Findings
- **GT7/Polyphony** [older, 2021-2022]:
  - **Scanning:**
    - Vehicle-mounted laser scans cover "road surface, run-off areas, track furniture, and buildings nearby".
    - Fixed scanners capture about a 50 m radius at the highest precision; LIDAR on cars, drones, helicopters and aircraft covers the wider geography.
    - About 10 people travel and take up to 80,000 photos, plus 360° 8K video from a car.
  - **From scan to track:**
    - Point clouds are used as reference to hand-build the environment.
    - "The entire process takes at least six months".
    - Trees are the hardest element.
  - **CEDEC 2022:**
    - Photogrammetry from a vehicle at about 10 mph and 30 fps; one Spa pass produced about 8 TB.
    - The sky and reflective areas are masked out of the photos.
    - Tracks were accurate enough for FIA certification.
    - Fictional tracks add buildings that follow local planning regulations to break up the landscape.
  - Sources: [GTPlanet, How Gran Turismo is Made](https://gtplanet.net/how-gran-turismo-is-made); [GTPlanet CEDEC 2022](https://www.gtplanet.net/pd-circuit-scanning-creation-techniques-20220831/)
- **Forza Motorsport (2023)** [older]:
  - Photogrammetry and laser-scanned imagery allowed "highly detailed vegetation and overgrowth". — [GTPlanet, Forza Motorsport everything so far](https://gtplanet.net/forza-motorsport-everything-so-far-20220614)
  - Maple Valley was reworked with many overhanging trees along the edge to show off the new foliage. — [Pure Xbox on Digital Foundry](https://purexbox.com/news/2023/10/forza-motorsport-a-pleasing-upgrade-over-forza-7-says-digital-foundry)
  - In-race ray tracing (reflections and AO) is on during racing. — [VGC](https://www.videogameschronicle.com/news/forza-director-insists-were-not-misleading-you-over-in-game-ray-tracing/)

### Inferences
- **Trackside detail priorities**, from the camera's point of view at racing speed:
  1. Road surface and kerbs.
  2. The first barrier line (armco, tyre walls, catch fences, advertising boards).
  3. Corner markers, marshal posts and distance boards.
  4. Tree lines and grandstands framing the horizon.
  5. Everything else.
- **Specific prop techniques:**
  - **Tyre walls:** model one 6-10-tyre stack (about 1-2k triangles at LOD0, a box at LOD2) and place thousands via `InstancedMesh2` along the barrier path generated from XML `barrier` segments.
  - **Armco and concrete walls:** loft cross-sections with `LoftGeometry` along the barrier offset (one mesh per chunk, lightmapped).
  - **Catch fences:** a lofted strip with an alpha-tested chain-link texture plus A2C. Wire fences alias badly at distance. Fade the alpha with distance (or swap to a semi-transparent grey strip beyond about 60 m) to avoid moiré, which is worse at 4K.
  - **Grandstands:** a few modular, lightmapped `BatchedMesh` pieces. Crowds can be instanced low-poly cards with colour variation (Forza's "Trees and Crowds" emphasis).
- **Automating LOD like Forza:** run meshoptimizer `simplify` (MIT; used by the agargaro demo) in the build pipeline for every prop. Generate LOD1/LOD2 automatically and author only LOD0.
- **Don't scan; stylise-realistic.** The project has no laser scans. Speed Dreams centre lines plus DEM terrain plus CC0 PBR textures plus a good lighting bake is the achievable "Forza-like" target. Polyphony's own fictional tracks (Kyoto, High Speed Ring) show that fictional circuits can still feel real when grounded in real regional vegetation and planning.
- **Budget targets per track** (estimates, for M1 at 1 viewport; halve the instances for 4 viewports):
  - About 2,000-6,000 unique static meshes, merged into fewer than 300 draw calls via `BatchedMesh` per material and chunk.
  - About 20-50k instanced props (cones, boards, tyres, posts).
  - About 5-30k trees (mostly impostors).
  - 0.5-1.5 GB GPU texture memory, all KTX2.

## 8. Practical pipeline: Speed Dreams XML layouts (centre line from segments) to a modern track. Procedural generation in code vs authoring in Blender (CLI scripting) vs hybrid

### Takeaway
Use a hybrid with one source of truth. A TypeScript/Node "trackgen" in the repo:
1. Parses the Speed Dreams XML.
2. Integrates segments into a centre line with elevation, banking and per-side widths.
3. Emits the physics mesh and the visual corridor mesh (road, sides, borders/kerbs, barriers via cross-section lofting) plus the terrain heightfield and placement data.

Blender is then driven headlessly to add authored dressing (grandstands, buildings, hero props), bake lightmaps/AO and export glTF. Because visuals and physics come from the same code-generated corridor, they never drift apart.

TORCS's own documentation warns that hand-editing the generated road mesh breaks physics alignment. SuperTuxKart shows that Blender plus Python add-ons is a workable track editor.

### Cited Findings
- **XML segment model:**
  - Segments are `str` (`lg`) or `lft`/`rgt` (`radius`, `arc`, optional `end radius`), in driving order.
  - Elevation via `z start`/`z end` or `grade`; banking via `banking start`/`banking end`.
  - Vertical profile `linear` or `spline` with `profil steps` / `profil steps length`. For splines, steps = `int(length / profil steps length) + 1` when `profil steps` is 1.
  - Sides can taper (`start width`/`end width`). Borders have `style` `plan`/`curb`/`wall`; barriers have `style` `fence`/`wall`.
  - [TORCS track manual](https://torcs.sourceforge.net/api/track_manual.html)
- **trackgen's output:**
  - AC3D (`.ac`) with axis mapping x_torcs = x_ac3d, y_torcs = -z_ac3d, z_torcs = y_ac3d. The origin is the minimum corner of the track bounding box.
  - Scenery and 3D objects are "added separately in AC3D or Blender"; adding scenery is a safe post-edit.
  - "Editing [the final road mesh] directly (moving, rotating, or scaling) breaks alignment with physics".
  - [TORCS track manual](https://torcs.sourceforge.net/api/track_manual.html)
- **OpenRacing trackgen modernisation plan:** to export "not only AC3D, but also Ogre XML Mesh or even Collada". Status: blocked. — [Launchpad blueprint [older]](https://blueprints.launchpad.net/openracing/+spec/trackgen-or)
- **SuperTuxKart:** Blender extended "so that the necessary options can be set in Blender's GUI" and exported with the map. — [SuperTuxKart blog [older]](https://blog.supertuxkart.net/2012/04/blender-as-game-editor.html)
- **r186 `LoftGeometry`** skins cross-sections that may change shape along the path, with open-strip mode via `closed: false`. — r186 source, [LoftGeometry.js](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/geometries/LoftGeometry.js)
- **Blender batch baking** via Python/Cycles is established (lightmap-bakery, The Lightmapper). — [lightmap-bakery](https://github.com/subgression/lightmap-bakery); [The Lightmapper](https://github.com/lordloki/The_Lightmapper)
- **AC modding split:** geometry/UVs in Blender, materials in the engine's editor. — [assettocorsamods.net](https://assettocorsamods.net/threads/assetto-mods-and-track-creation.3349)
- **Current project:** track code already exists (`track/track.ts`, `trackGeometry.ts`, `trackPhysics.ts` with tests, `terrain.ts`, `cornicheRun.ts`), and scenery modules (`scene/scenery.ts`, `sceneryModels.ts`, `trackVisual.ts`). The Corniche theme is being dropped per owner decision. — local repo (`client/src/games/splitways/track/`, `scene/`)

### Inferences
- **Recommended pipeline** (all build-time scripts in `scripts/` or a `tools/trackgen` package):
  1. **Parse:** read the Speed Dreams XML into a typed `TrackDef` (segments, sides, borders, barriers, surfaces, pits, start). Keep the XML's Free Art License attribution with the derived data.
  2. **Integrate the centre line:**
     - Walk segments: heading += arc for curves (with the radius interpolated from `radius` to `end radius` for spiral/clothoid-like segments), position += tangent × ds.
     - Sample at 0.5-1 m steps (finer than `profil steps length`) to get position, tangent, curvature, banking (interpolated start→end) and elevation (spline profile per the XML semantics).
     - Close the loop and distribute any closure error along the lap.
     - Build a parallel-transport frame with the banking roll applied.
  3. **Rescale/retheme** for the 3.3 km / 5.9 km / 3.8 km targets: choose Speed Dreams layouts close in length and character (a club circuit, a fast Monza-like circuit, a mountain road), then adjust widths, elevation amplitude and kerbs in a small JSON override file instead of editing the XML.
  4. **Generate the corridor (code):**
     - Cross-section templates per station: road (crowned/banked), left/right side (run-off: grass/gravel/asphalt per `surface`), border (kerb profile per `curb` height, sawtooth option), barrier (wall/fence height).
     - Loft into chunked meshes of about 100-200 m (for culling and lightmap pages) using `LoftGeometry` or the existing `trackGeometry.ts`.
     - UV0 = tiling (metres), UV1 = lightmap (packed later in Blender, or by xatlas in code), UV2 = track space (u across, v along).
     - Emit the physics trimesh from the same stations (road + sides + kerbs) and surface IDs per triangle for grip, rumble and audio.
  5. **Generate terrain (code):**
     - Heightfield from a DEM tile (Copernicus GLO-30, with attribution) or procedural noise, carved to the corridor with a distance field and shoulder blend.
     - Splat weights from slope, height, corridor distance and an optional paint mask.
     - Emit LOD chunks.
  6. **Generate placements (code):**
     - Scatter trees, bushes, grass density, tyre stacks, boards, marshal posts and distance boards from rules (distance from the corridor, slope, a corner/braking-zone table derived from curvature) with seeded randomness.
     - Output as instance arrays (position, yaw, scale, species) in a compact binary file, not as Blender objects.
  7. **Author (Blender, optional per track):**
     - Import the generated corridor + terrain glTF as locked reference.
     - Artists place grandstands, pit building, bridges and hero props (a Blender Python add-on panel, SuperTuxKart-style, can tag objects with game metadata).
     - Never edit the corridor in Blender; change the XML/JSON and regenerate.
  8. **Bake (Blender CLI):** `blender -b track.blend --python bake.py`:
     - UV-pack lightmap charts and bake AO/sky-visibility (and full irradiance per ToD preset).
     - Denoise, save EXR.
     - Export the dressed scene glTF with `TEXCOORD_1`.
  9. **Package:** gltf-transform (meshopt/Draco, dedupe, KTX2 via `toktx`/`basisu`), instance binaries, the light-probe layout, and a track manifest JSON (sky preset per ToD, fog parameters, sun keyframes, `SunLight` settings).
  10. **Runtime:**
      - Load the manifest, corridor chunks, terrain chunks and instance sets.
      - Create `InstancedMesh2`/impostor sets.
      - Bake `LightProbeGridWebGL` during the countdown.
      - Set `material.lightMap` (`channel = 1`).
- **Why hybrid beats either extreme:**
  - **Pure code:** fast iteration and guaranteed physics alignment, but buildings and hero props look generic.
  - **Pure Blender:** best art control, but the centre line, physics and kerbs drift, and every layout change is manual.
  - **Hybrid:** keeps the drivable surface procedural (one source of truth) and puts human effort only where it shows (landmarks, grandstands, the lighting bake).
- **Per-track effort estimate** (inference): with the generator in place, a new track is a JSON override plus a placement-rule tune plus optional Blender dressing plus an overnight bake. That is days, not months. The generator itself is the main engineering investment.
- **Order of work:**
  1. Generator for the 3.3 km club circuit, with no bake, using `SunLight` and blob AO.
  2. Vegetation/impostor system.
  3. Blender bake pipeline.
  4. Monza-like 5.9 km (grandstands, long tree-lined straights; impostor-heavy).
  5. Mountain road (DEM terrain, triplanar rock, backdrop ring, no grandstands).
